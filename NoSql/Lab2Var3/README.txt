# Tourism Ecosystem (Екосистема Туризму)

Цей проект є реалізацією лабораторної роботи з дисципліни "Бази Даних / NoSQL". Проект демонструє побудову надійної архітектури доступу до даних, використання гібридного підходу (Polyglot Persistence) та порівняльний аналіз продуктивності реляційної (PostgreSQL) та документо-орієнтованої (MongoDB) баз даних.

## 🛠 Технологічний стек

* **Платформа:** .NET 9 (C#)
* **Реляційна БД:** PostgreSQL 16
* **NoSQL БД:** MongoDB
* **ORM / Data Access:** Dapper (для SQL), MongoDB.Driver (для NoSQL)
* **Патерни:** Repository, Unit of Work, Transaction Script (у Stored Procedures)

## 📋 Реалізований функціонал

### 1. Реляційна частина (PostgreSQL)
Архітектура бази даних спроектована з акцентом на безпеку та цілісність даних:
* **Інкапсуляція логіки:** Доступ до таблиць закритий.
    * **Читання:** Тільки через **Views** (наприклад, `v_active_tours_with_rating`), які фільтрують "м'яко видалені" записи.
    * **Запис:** Тільки через **Stored Procedures** (наприклад, `sp_create_booking`), що гарантує атомарність транзакцій.
* **Audit & Soft Delete:** Реалізовано автоматичний аудит змін (`updated_at`, `updated_by`) через тригери та механізм "м'якого видалення" (Soft Delete).
* **Патерн Unit of Work:** Реалізовано складну транзакцію створення бронювання, де вставка в `Bookings` та `BookingItems` відбувається атомарно на стороні БД.

### 2. NoSQL частина (MongoDB)
Реалізовано гібридну архітектуру для зберігання складних даних:
* **Каталог турів:** Детальна інформація про тур, гнучкі атрибути (Tags, Difficulty) та вкладені відгуки зберігаються в одному JSON-документі.
* **Embedding:** Використано патерн вкладення даних для уникнення зайвих JOIN-операцій.

### 3. Бенчмаркінг (SQL vs NoSQL)
Проведено навантажувальне тестування для порівняння швидкодії читання даних.

#### Сценарій 1: Масова вибірка (100 000 вкладених записів) (пробував спершу так)
* **SQL:** Виконує `LEFT JOIN` між таблицями `Tours` та `Reviews`.
* **MongoDB:** Читає один великий документ з масивом відгуків.
* **Результат:** SQL з Dapper виявився швидшим у потоковому читанні, оскільки MongoDB витрачає значний час на десеріалізацію великих BSON-документів (CPU-bound операція).

#### Сценарій 2: Проблема Декартового добутку (Complex Data)
* **Умова:** Тур має 200 фото та 200 тегів.
* **SQL:** При спробі отримати все одним запитом відбувається вибух даних ("Cartesian Explosion"), повертаючи 40,000 рядків дубльованих даних.
* **MongoDB:** Ефективно повертає один документ без дублювання, демонструючи перевагу Document-моделі для складних агрегатів.
